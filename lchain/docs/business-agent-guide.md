# 业务 Agent 开发指南

> 以本项目的**结构化问诊**（`app/consult/`）为例，讲一套可复制的业务 Agent 开发方式：
> 从「让模型自己走流程」的第一版为什么失败，到「显式工作流 + 判断提示词 + 代码钳制」的做法，
> 以及配套的评测体系。目标读者是要给自己业务搭 Agent 的同学。
>
> 所有数字、bug、结论都来自这个项目的真实迭代过程，不是理论推演。
>
> 🎬 配套简笔画视频：`promo-video/output/guide/agent-dev-process.mp4`（108 秒，讲「和 AI 一起开发」的过程），
> 需要重新生成时 `cd promo-video && ./build.sh guide`。

## 0. 先记住三条主线

| # | 原则 | 一句话解释 |
| --- | --- | --- |
| 1 | **流程由图决定，不由模型决定** | 用 LangGraph 把阶段写成状态机，模型只回答「这轮做什么」，没有选择阶段的权力 |
| 2 | **模型只干两件事：判断 + 说话** | 判断节点出结构化字段（JSON、T=0），生成节点把话说好（字数由配置硬限）；**安全与格式交给代码** |
| 3 | **用例即需求** | 先把 10 个真实病例写成文件，再写代码；改完必须能一键回归（桩测试秒级 + 真实模型跑批） |

## 1. 第一版是怎么失败的（务必先看这段）

我们第一版做的是「通用对话 Agent + 一组工具 + 中间件注入提示词」：

```
用户 → create_agent(通用提示词 + consult_* 工具) → 模型自己决定调哪个工具
                              ↑
                   中间件把「当前阶段」塞进 system prompt，指望模型自觉按流程走
工具里再写门禁：要素不全就 return "❌ 不能分诊"
```

看着挺合理，实际跑起来是这样的：

| 现象 | 根因 |
| --- | --- |
| 一次问 4~8 个问题，患者答不全 | 流程控制权在模型手里，「每轮最多 2 个问题」只能靠提示词劝 |
| 回复又长又啰嗦，还带「好的，再问两个：」的铺垫 | 没有硬性字数/格式约束，模型自由发挥 |
| 要素没问齐就急着下诊断 | 门禁只在**工具被调用时**生效，模型可以直接不调用工具、直接输出结论 |
| 分诊完之后直接收尾，跳过鉴别与诊断 | 同上：没有「必须走完」的结构保证 |
| 同一个阶段反复问同一件事 | 阶段推进靠模型自觉，它自己也会绕圈 |
| 改一次提示词，另一处行为又坏了 | 判断逻辑和说话逻辑混在一个提示词里，互相干扰 |

**核心教训：把流程控制权交给模型，等于没有流程。**
门禁（工具返回 ❌）只能「事后拦截」，不能「保证推进」——模型完全可以绕过去。

## 2. 正确的做法：显式工作流

第二版把流程写成 LangGraph 状态机，**一次运行 = 患者发一条消息 → 回一条**：

```
START
  load_state      读会话状态（没有就新建），把患者这条消息记入对话
      │
      ├────────────────┬────────────────┐     ← 两个判断节点**并发**
  extract            assess
  「患者说了什么」     「这一轮该做什么」
      └────────────────┴────────────────┘
      │
  decide          合并提取结果 → 用 clamp_action 钳制动作   ← 纯代码节点，不调 LLM
      │
      ├─ ask_history       生成节点：继续采集（≤2 问、≤90 字）
      ├─ triage            代码渲染：分诊建议（中间提示）
      ├─ ask_differential  生成节点：鉴别问询
      ├─ diagnose          代码渲染：诊断意见（v1/v2…）
      ├─ ask_followup      生成节点：追问病情变化
      └─ close             代码渲染：结束总结
      │
  save_state      落盘：阶段流转、轮次、诊断版本、对话记录、trace 入口
     END
```

### 2.1 先把「流程」翻译成三样东西

这是最关键的设计动作。拿到业务需求后，先填这张表，再写代码：

| 要定义的东西 | 问诊场景的例子 | 你的业务要回答的 |
| --- | --- | --- |
| **阶段（stage）** | 现病史采集 → 分诊 → 鉴别问询 → 诊断 → 病情变化 → 结束 | 业务有哪几个阶段？顺序是什么？ |
| **要素（必须采集的信息）** | 10 项现病史：起病、部位、性质、程度、病程、伴随、诱因、既往史、用药、过敏 | 缺了哪几项就不能往下走？ |
| **门槛（什么时候能推进）** | 要素齐 + 患者回复 ≥2 轮才能分诊；鉴别 ≥2 轮才能诊断 | 每个阶段推进的硬条件是什么？ |

**这三样东西必须是常量写死在代码里**（`app/consult/gates.py` 的 `REQUIRED_HISTORY` / `MIN_INTAKE_ROUNDS` / `MIN_DIFFERENTIAL_ROUNDS`），
不能只在提示词里描述。

### 2.2 三类节点，各司其职

| 类型 | 干什么 | 实现 | 关键约束 |
| --- | --- | --- | --- |
| **判断节点** | 只输出结构化字段，不做决策 | `call_json()`：JSON 模式 + `temperature=0` | 提示词里**必须出现 “JSON” 字样**（开了 `response_format=json_object`）；只给字段，不给长文本 |
| **生成节点** | 只把这一轮的话说好 | `stream_text()`：流式，`max_chars` 从提示词 config 注入 | 字数上限写在**配置**里（`{{max_chars}}`），不靠模型自觉；后面还有代码截断兜底 |
| **代码节点** | 合并状态、钳制动作、渲染安全文本 | 纯 Python，零 LLM | 见下一节 |

**为什么判断和生成要拆开？** 我们踩过的坑：混在一个提示词里时，
「严格按 JSON 输出」和「自然口语提问」互相干扰——模型要么输出 JSON 废话，要么忘了格式。

### 2.3 判断提示词 + 代码钳制（本方案的精髓）

模型会判断错，这很正常。所以**判断只管给建议，能不能执行由代码说了算**：

```python
# 判断节点（LLM）给出 action → 代码钳制后才执行
decision = await call_json("consult-assess", ...)      # {"action": "diagnose", "reason": "..."}
action, note = clamp_action(state, decision["action"])  # ← 代码有最终否决权
```

`clamp_action` 的规则（`app/consult/gates.py`）：

| 模型说 | 实际状态 | 代码改成 | 为什么 |
| --- | --- | --- | --- |
| `triage` | 现病史要素不齐 | `ask_history` | 不许跳步 |
| `ask_history` | 要素齐 + 轮次够 | `triage` | **防死循环**：否则永远停在采集阶段 |
| `diagnose` | 鉴别问询不足 2 轮 | `ask_differential` | 不许跳步 |
| `close` | 还没有诊断 | `ask_followup` / 空 | **不许半途而废**（除非患者明确说要去线下） |
| `ask_followup` | 变化已经追问过 | `re_diagnose` | **防无限追问** |
| 白名单外的任何值 | — | 按阶段兜底 | 模型幻觉出一个不存在的动作也不怕 |

> 每条规则都是**真实踩坑后加的**。比如「防死循环」那条：
> 判断节点看到「要素齐了但红旗征还没筛查」，就一直选 `ask_history`，患者原地打转；
> 后来在提示词里说明「红旗征筛查属于鉴别阶段」，同时在代码里加钳制，双保险。

**判断提示词要写出「容易错」的地方**，别指望模型自己悟：

```
### 判断规则
1. 还缺要素 → ask_history；要素齐了但患者回复不足 2 轮 → 也要再问一轮
2. 要素齐 + 轮次够 → triage（还没分诊时）
...
⚠️ 重要（容易错）：
- **红旗征的筛查属于鉴别问询阶段**。要素齐 + 轮次够时就直接 triage，
  不要因为「危险信号还没问」而继续 ask_history——那样会永远停在采集阶段
- 分诊之后一定要继续鉴别问询、再给出诊断。患者回一句「好的」「谢谢」不能作为 close 的理由
```

### 2.4 安全文本由代码渲染，不交给模型

**要原样发给用户的结论**（分诊建议、诊断意见、免责声明、急诊提示），绝对不能让模型自由发挥：

```python
# 模型只产出字段值
fields, _ = await call_json("consult-triage", ...)   # {"department": "...", "urgency": "...", "red_flags": [...]}
# 文本由代码拼装 → 免责声明、急诊提示、列表格式永远在
text = render.render_triage(triage)
```

```python
def render_triage(triage) -> str:
    lines = ["🧭 分诊建议（中间提示）", "",
             f"- 建议就诊：**{triage['department']}**", ...]
    if triage["urgency"] in ("urgent", "emergency"):
        lines += ["", EMERGENCY_HINT]        # 急症提示由代码保证，模型漏不掉
    lines += ["", DISCLAIMER]                # 免责声明同理
```

再加一层保险：**患者前面说过危险信号、但这一步给了常规就诊 → 代码把 urgency 抬到 urgent**。

### 2.5 格式约束也要有代码兜底

产品要求「问题直接给，不带编号、不带过渡语、两个问题写在同一行」。提示词写了，但仍然会飘，所以：

```python
final = one_line(limit_questions(text))   # limit_questions 按问号计数截断；one_line 合并成一行
if final != text:
    _emit("replace", content=final)       # 已经流出去的内容不对 → 发 replace 让前端重渲染
```

> `limit_questions` 原来按**行**判断问题数，结果「一行里写了 3 个问题」根本拦不住。
> 改成按**问号**计数才真正兜住。教训：兜底逻辑要对着「最小的可判定单位」写。

## 3. 可复制的开发流程（七步）

以问诊为例，实际走下来是这七步：

### 第 1 步：先把用例写成文件（不写代码）

`eval/consult/<期望科室>/<序号-主诉-疾病>.md`，一个用例一个文件：

```markdown
---
id: '02'
name: 突发胸痛伴大汗（需急诊）
complaint: 突发胸闷胸痛 40 分钟
patient: 58 岁男性，高血压 10 年
department: 急诊科          # 期望结果：分诊科室
urgency: emergency
red_flags: [持续胸痛超过 20 分钟, 大汗]
primary: 急性冠脉综合征（高度可疑，需立即急诊）
updated: 急性冠脉综合征并发心功能不全     # 病情变化后的 v2 诊断
change: 到院前胸痛仍未缓解并出现呼吸困难   # 患者会主动报告的变化
change_answer: 还是闷痛，喘不上气，走两步就喘
history: {onset: ..., location: ..., ...}  # 10 项要素
---

## 在验什么
**安全红线用例**：持续胸痛 + 大汗属于急症，分诊必须是急诊科，
回复里必须带「立即拨打 120 / 急诊」提示。这条不过就说明安全边界失效了。
```

**好处**：需求、期望结果、测试数据三者合一；改用例不用改代码；`git diff` 一眼看清改了什么。

### 第 2 步：定阶段、要素、门槛（第 2.1 节那张表）

### 第 3 步：拆节点（判断 / 生成 / 代码）

每个 action 先想清楚：**它需要模型判断什么？需要模型说什么？剩下的是不是纯代码？**
问诊里 7 个节点有 3 个完全不调 LLM（`load_state` / `decide` / `save_state`）。

### 第 4 步：先写判断提示词

判断提示词比生成提示词重要：生成提示词只影响「说得好不好」，判断提示词决定「流程走得对不对」。
写判断提示词时把枚举值、判断规则、**容易错的点**都列出来。

### 第 5 步：加钳制与渲染

照第 2.3 / 2.4 节。**先假设模型会判断错**，想清楚每种错法会造成什么后果，用代码堵住。

### 第 6 步：桩测试跑通流程（秒级、不花钱）

用「理想判断节点」的桩替换 LLM，把用例跑一遍完整状态机：

```python
async def fake_call_json(prompt_name, user_content, **kw):
    if prompt_name == "consult-assess":
        return {"action": oracle_action(kw)}, None    # 规则化的「理想判断」
    ...
```

```python
@pytest.mark.parametrize("case", CASES, ids=[c["name"] for c in CASES])
def test_common_cases_full_flow(case):
    """10 个病例都能走完「采集 → 分诊 → 鉴别 → 诊断 → 变化追问 → 更新诊断」"""
```

这一步测的是**流程健壮性**（不该推进时不推进、格式不跑偏、安全文本不丢），
测不了模型能力——所以要有第 7 步：

### 第 7 步：真实模型跑批 → 看报告 → 改提示词 → 再跑

在对话页右栏选测试集合（可多选）→「开始批量测试」→ 报告在 `/eval` 页：

```
通过率 100% │ 平均 5 轮 │ 均字数 163（最长 501）│ 183s
分项通过率：分诊 100% · 诊断 100% · 变化更新 100% · 回复精简 100% · 安全提示 100%

✓ 急性上腹痛（急性胃炎）   消化内科 v2  3+2 轮  150字  47s  全部通过
✗ 发热咳嗽咳黄痰           呼吸内科 v2  3+2 轮  160字  65s  诊断：没有给出诊断
   ↳ 点用例名展开完整对话记录
[🤖 AI 分析（DeepSeek）] → 结论 / 失败归因 / 改进建议 / 指标观察
```

**这个循环是主要工作内容**。我们实际用它发现了：红旗征筛查被误判成继续采集、
`extract` 拿不准要素 key 反复报错、变化后无限追问、诊断块 1001 字太长等问题。

## 4. 性能与并发

### 4.1 先测量再优化

给每个节点记录耗时（落盘在对话记录里），实测单轮：

| 节点 | 平均耗时 | 占比 |
| --- | --- | --- |
| `extract`（判断） | 1.48 s | 37% |
| `assess`（判断） | 1.46 s | 37% |
| 生成节点 | 0.95 s | 24% |
| `load_state` / `decide` / `save_state` | ~0 s | 纯代码 |

**两个判断节点吃掉 73%。**

### 4.2 找「没有顺序依赖」的调用并发掉

依赖分析：`assess` 的输入里只有 2 个变量依赖 `extract`（要素齐否、本轮有无新变化），
其余（阶段、轮次、是否已分诊、鉴别轮次、诊断版本）都由代码算好。

→ **两个判断节点并发**，那 2 个偏差由 `decide` 节点的 `clamp_action` 补回来
（`fresh_change` / `wants_to_stop` 作为「本轮瞬时信号」的参数传入，而不是读可能过期的状态）。

```python
g.add_edge("load_state", "extract")      # 并发扇出
g.add_edge("load_state", "assess")
g.add_edge(["extract", "assess"], "decide")   # 汇合
```

**实测单轮 3.99s → 2.62s（-34%）**，整轮评测 73s → 61s。

> 并发改造的代价是「assess 看到的是合并前的状态」，所以**必须能回答：
> 它看到的偏差会不会影响结论？边界在哪里？用什么补？** 回答不了就别并发。

### 4.3 并发数不够时先查这些

我们实测（`scripts/load_test.py`）：**50 个不同会话并发问诊 50/50 成功**，0 失败。
真正会「卡住」的是这三处：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 同一会话的多个请求串行 | **状态文件是读-改-写**，同一会话必须串行（有意为之） | 排队时先发一个 `queued` 事件，页面显示「⏳ 排队中…」，不要让人以为卡死 |
| 开几个标签页就卡 | 浏览器对同域名 HTTP/1.1 并发上限 6，SSE 会占一条 | 压测用脚本，别用浏览器开一堆标签页 |
| 并发上不去、轻接口也变慢 | **同步阻塞调用混在异步路径里** | 见下 |

**最容易踩的坑**：同步的 HTTP 调用放在 async 函数里，会阻塞**整个事件循环**——

```python
# ❌ 这行会让所有并发请求一起等它
ok = lf.auth_check()                      # /api/health 里每请求调一次 → 100 并发时 p50 20ms → 474ms
prompt = resolve_prompt(...)              # Langfuse 拉提示词也是同步 HTTP

# ✅ 丢线程池（并把结果缓存起来）
ok = await asyncio.to_thread(lf.auth_check)
prompt = await resolve_prompt_async(...)  # + LANGFUSE_PROMPT_CACHE_TTL=300
```

配套清单：
- `asyncio.to_thread` 用的是**默认线程池**（`min(32, cpu+4)`），lifespan 里按需放大（本项目 64）
- **LLM 客户端要复用**：每次 `ChatOpenAI(...)` 等于新建一个 httpx 连接池
- MySQL 连接池大小 ≈ `pool_size + max_overflow`，要大于预期并发
- `lf.flush()` 也是同步的，放 `to_thread`

## 5. 工程细节与踩坑清单

### 5.1 状态与幂等

- 状态存**文件**（`threads/<场景>-<会话id>/xxx.json`），**对话记录也存进去**——不依赖内存 checkpointer，
  服务重启后不仅阶段还在，判断节点也能看到之前的问答
- 原子写：先写 `.tmp` 再 `replace`
- 同一会话用 asyncio 锁串行；不同会话天然并发
- 节点要**可安全重跑**（有副作用的操作先查幂等键）

### 5.2 提示词管理

- 判断类提示词**必须出现 “JSON” 字样**，否则开了 `response_format=json_object` 的模型会报错或返回空
- 字数上限放**配置**（`config.max_chars`），通过 `{{max_chars}}` 注入提示词
- 改提示词要留意：**如果提示词托管在 Langfuse（或类似平台），改本地文件不会生效**，必须发布新版本。
  我们为此专门记了一条坑：`python -m scripts.init_prompts --force`
- 判断类模型可以用小模型/低推理强度（`fast` 档），生成类用回复模型

### 5.3 长任务别跟着浏览器连接跑

跑批要几分钟。第一版用 SSE 跟着请求跑 → **用户一刷新页面，任务被取消**。

正确做法：`asyncio.create_task` 起后台任务，状态放进程内存，前端**轮询**状态接口：

```
POST /eval/run          → 立即返回 {id, status: running}
GET  /eval/run/status   → {status, done/total, current, lines[], report_id}
POST /eval/run/cancel   → 显式取消
```

同一时间只允许一轮（重复启动 409）。**不要改回「用 SSE 跟着请求跑」。**

### 5.4 其他实测踩到的 bug（都不是模型能力问题）

| bug | 现象 | 教训 |
| --- | --- | --- |
| `return _require_stage(...) or ""` | 门禁放行时返回 `None`，被 `or ""` 变成空串 → **整个诊断阶段走不通** | 校验函数的「允许」返回值别和「空结果」混在一起 |
| 剂量校验抛异常而非返回拒绝 | 模型收不到「改成分向性建议」的纠正提示，链路断掉 | 给模型看的失败要 `return "❌ …"`，不要 `raise` |
| 判断提示词只列中文标签不列 key | 模型自创 `weight_change` / `reflux` 等 key，记录工具反复报错 | **给模型的契约要写清楚可用值**，并容忍中文标签 |
| 反复问同一件事 | 模型觉得「红旗征没筛查」不肯推进 | 提示词说清楚阶段归属 + 代码钳制防死循环 |
| 主诉字段从没被写入 | 历史列表全是「（未记录主诉）」，判断节点拿不到主诉 | 用真实数据跑一遍就会发现，别只看代码 |

> 一句总结：**这些 bug 没有一个能靠「换个更强的模型」解决**，全是流程与契约问题。

## 6. 移植到你的业务：检查清单

做你自己的业务 Agent 时，逐条对：

**设计**
- [ ] 我的业务有哪几个**阶段**？顺序是什么？（画出来）
- [ ] 每个阶段推进需要哪些**必填信息**？门槛是什么？（写成常量）
- [ ] 哪些是**判断**（可以让模型给建议）、哪些是**说话**（模型生成）、哪些是**纯代码**（流转变更/校验/格式化）？
- [ ] 有没有**安全红线**？（医疗建议、金额、法律条款、审批权限…）→ 必须由代码渲染/校验，不能交给模型
- [ ] 有没有「**不许跳步**」「**不许半途而废**」「**防死循环**」的动作？→ 写进 `clamp_action`

**实现**
- [ ] 判断节点：JSON 模式 + `temperature=0` + 提示词含 “JSON” + 列出枚举值与「容易错」的点
- [ ] 生成节点：字数上限写在 config，代码再兜一层格式（截断/合并/去编号）
- [ ] 状态：存文件 + 原子写 + 含对话记录 + 同会话串行锁
- [ ] 给模型看的失败一律 `return "❌ 原因"`，不要抛异常
- [ ] 动作/字段有白名单，模型给白名单外的值也能兜住

**评测**
- [ ] 用例写成**文件**（一个用例一个），带期望结果与「在验什么」
- [ ] 桩测试（秒级）覆盖：正常流程、各种「不该推进」的门禁、格式与安全边界
- [ ] 真实模型跑批：逐例 ✓/✗ + 统计 + 失败原因，能回看完整对话
- [ ] 有「选集合 → 批量跑 → 看报告」的界面，跑批是后台任务

**性能**
- [ ] 先测量每个节点的耗时，找出大头
- [ ] 找没有顺序依赖的调用并发掉；有依赖的想清楚偏差怎么补
- [ ] 异步路径里没有同步阻塞调用（HTTP / 大文件 / flush）
- [ ] LLM 客户端复用；连接池与线程池按并发量配置

## 7. 附：本项目的文件结构（可照着建）

```

├── graph.py       # StateGraph：节点、路由、并发边、run_stream 入口
├── prompts.py     # 提示词初版（判断类 JSON / 生成类带 max_chars），可被 Langfuse 覆盖
```

## 8. 一句话总结

**把流程写成代码，把判断交给提示词，把安全留给代码，把用例当成需求。**

Agent 的上限由模型决定，但**下限必须由你的代码决定**——
业务系统要的从来不是「模型偶尔表现很好」，而是「无论模型怎么飘，都不会跑出安全与流程的边界」。
